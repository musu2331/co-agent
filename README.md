# co-agent

一个让 **Codex、Pi、DeepSeek Harness（DSH）共用项目文件、接续任务的本机可视化协作框架**。

在同一个 WebUI 中选择项目、选择工具和模型，创建任务、查看答复，再将上下文转交给下一款工具。项目文件始终位于自己的原目录，协作台统一记录任务与结果。

**这是一套可扩展的起点。欢迎根据个人需求自行拓宽框架，接入更多工具、模型、任务流程与界面功能。**

## 功能

| 功能 | 说明 |
| --- | --- |
| 项目目录共享 | 登记本机已有目录，Codex / Pi / DSH 在同一个原目录工作，无需复制项目 |
| 可视化任务工作台 | 创建、排队、执行、停止、筛选任务，查看日志与结果，导入和下载 Markdown |
| 上下文交接 | 将上一轮要求与答复带入新任务，切换工具继续处理 |
| 独立模型配置 | 为三款工具分别保存默认模型；新建或转交时可单独覆盖；保存模型配置快照 |
| 模型推理强度 | Codex、Pi 可配置支持的推理强度；Pi 可使用已有提供方配置 |
| 官方账号复用 | 使用原工具已登录的账号；DSH 使用本地已保存的官方账号，无需在协作台填写令牌 |
| 本地会话同步 | 按需只读导入三款工具已有项目和保留会话，排除支持的归档及内部记录 |
| 外部完成关联 | 工作已在其他工具完成时，关联原会话与结果，保留失败历史并停用重复重试 |
| 每周后台维护 | 独立处理废弃项目的协作台索引与临时文件，维护记录不进入任务工作台 |
| 无数据分发 | 通过白名单导出代码、结构和空配置，排除原项目、任务历史、日志和凭据 |

后端使用 **Python 标准库**，前端为原生 HTML / CSS / JavaScript，无需 pip 依赖或前端构建。当前主要验收平台是 Windows；其他系统的 CLI 路径适配可按需扩展。

## 快速开始

需要 Python **3.12+**。根据自己的需求安装 Codex、Pi 或 DeepSeek Harness，并在各自原工具中登录。可以只安装其中一款；Pi 和部分 npm 安装方式需要 Node.js。

```bash
git clone https://github.com/musu2331/co-agent.git
cd co-agent
```

Windows 下双击 `打开项目协作台.vbs` 或 `open-webui.cmd`。首次启动会从 `config/` 中的示例生成缺失的本机配置，已有配置会保留。

也可让 AI 或终端执行：

```bash
python -B setup_workspace.py
python -B webui.py --launch
```

Windows 的 Python Launcher 用户可将 `python` 换成 `py -3`。默认打开 `http://127.0.0.1:8766/`；被其他副本占用时会选择后续端口，请以启动器打开的地址为准。

首次使用：

1. 在“项目映射”中登记自己的项目目录。
2. 如需导入原工具会话，自行开启本机来源自动同步；初始默认关闭。
3. 在“模型配置”中选择各工具默认值，或在新建任务时指定本次模型。
4. 先存为待办核对内容，再按需执行；任务结束后可带上下文转交。

详细环境、DSH 安装路径、数据结构与排查方法见 [REPLICATE.md](REPLICATE.md)。

## 直接交给 AI 部署的提示词

将下面整段复制给能访问本机文件和终端的 AI 助手。它会完成检查、部署和验收；账号登录由你在原工具中完成。

```text
请帮我在本机部署 co-agent：
https://github.com/musu2331/co-agent

请直接完成必要的本地部署和验证，不要只给操作建议。

1. 先确认操作系统、Python 版本和可写工作目录。需要 Python 3.12+；这是 Python 标准库项目，不需要 pip install。检查 Git、Node.js，以及我已安装的 Codex、Pi、DeepSeek Harness。不要假定三款工具必须全部安装。
2. 将仓库克隆到一个新的 co-agent 目录；如果已有该仓库，先检查现有修改，再决定复用或更新。不要覆盖现有项目和本机配置。
3. 阅读 README.md、REPLICATE.md、COMMON.md 以及适用的项目指令。当前主要验收平台是 Windows；其他系统请核对 bridge.py 中的 CLI 路径和原工具 --help。
4. 在仓库根目录执行：python -B setup_workspace.py。Windows 若只有 Python Launcher，使用 py -3 -B setup_workspace.py。初始化只生成缺失配置，不覆盖已有配置。
5. 执行离线验证：python -B -m unittest discover -s tests -v。若 Node.js 可用，再执行 node --check web/app.js。测试使用临时目录和模拟 CLI，不要为了验收擅自调用真实付费模型。
6. 执行 python -B webui.py --launch（或 py -3 -B webui.py --launch）。保持服务只监听本机回环地址，核对实际打开的端口；必要时查看本机 state/webui.log。
7. 验证页面能打开、项目映射为空、本机来源自动同步默认关闭、模型配置可打开。通过 /api/health 核对服务状态。工具版本探测成功只表示命令可启动，不表示账号或模型一定可用。
8. 指导我在“项目映射”中登记已有目录，在“模型配置”中选择模型。若缺少项目目录或我对模型的选择，请向我询问。需要登录时让我在原工具中操作，不复制或打印 API Key、令牌或原始凭据文件。
9. 未经我明确要求，不执行真实业务任务，不启动训练或部署其他业务，不改变各工具的权限和审批设置，不开放公网访问。
10. 最后给我：本机访问地址、启动方式、检测结果、尚需我完成的登录或工具安装，以及下一步如何通过 WebUI 新建和转交任务。

部署完成后，我可以根据个人需求继续拓宽这个框架。请先使当前版本可靠运行，再讨论扩展。
```

常用命令：

```bash
# 显式初始化；首次 WebUI 启动也会自动执行
python -B setup_workspace.py

# 后台启动并打开页面
python -B webui.py --launch

# 后台启动但不自动打开浏览器
python -B webui.py --launch --no-browser

# 前台运行，便于排查
python -B webui.py --serve --port 8766

# 离线测试
python -B -m unittest discover -s tests -v

# 导出独立的无数据副本和 ZIP；目标名称需要尚不存在
python -B export_release.py --output ../my-co-agent-template
```

## 根据个人需求拓宽框架

你可以按自己的工作习惯 Fork、修改和定制。建议从一个明确的小需求开始，保留现有默认行为，补充验证后再逐步扩展。

| 扩展方向 | 主要入口 |
| --- | --- |
| 接入其他编程助手或本地 CLI | `bridge.py` 的工具定义、探测和命令适配，同时调整模型与前端选项 |
| 更多模型与提供方配置 | `model_config.py`、各工具命令适配及模型配置界面 |
| 新的项目或会话来源 | `sources.py`，按原工具保存格式增加只读适配 |
| 多阶段工作流、提示词模板、审核步骤 | `webui.py` 的任务与交接逻辑、`COMMON.md`、`contexts/` |
| 团队协作与远程使用 | 在现有本机模式之外单独设计认证、授权、隔离和审计 |
| 更丰富的可视化操作 | `web/index.html`、`web/app.js`、`web/style.css` |
| 清理与归档策略 | `maintenance.py`，保持对真实项目与原会话的边界 |

给 AI 的扩展提示词也可以这样写：

```text
请在 co-agent 现有结构上增加【我的具体功能】。
先阅读 README.md、REPLICATE.md、COMMON.md 和适用项目指令，确认当前任务、模型配置和权限边界。
给出改动范围后完成最小可用实现，保留已有配置与任务记录，补充有意义的测试并更新文档。
不要把原工具凭据、真实项目路径或任务历史写入要提交的代码；不要为通过测试而跳过原工具权限。
完成后说明功能入口、验证结果和后续可扩展点。
```

## 结构

```text
co-agent/
  bridge.py              工具适配、任务执行与项目协作锁
  webui.py               本机 HTTP 服务、任务与交接 API
  model_config.py        模型设置、候选读取与参数校验
  sources.py             本地项目和会话只读同步
  maintenance.py         独立后台维护
  setup_workspace.py     从示例初始化缺失的本机配置
  export_release.py      无数据导出器
  config/                可公开的空配置示例
  contexts/              通用示例与本机项目上下文
  web/                   页面、样式、脚本和图标
  tests/                 离线测试
  tasks/                 本机任务与结果，运行数据不提交
  state/                 本机日志、索引、锁和维护历史，不提交
```

`projects.json`、`model-config.json`、`app-settings.json` 在本机初始化，已由 Git 忽略。仓库提交的是 `config/*.example.json`。个人上下文、任务日志、账号验证记录、模型权重和原工具会话不进入共享仓库。

## 运行边界

- 账号和凭据由原工具管理。保存模型设置或待办不会调用模型。
- 模型候选来自本机缓存，不保证当前账号支持；实际执行仍受登录、额度和工具版本限制。
- 每个项目的桥接任务串行执行；协作锁无法阻止原工具侧手工发起的并行修改。
- Codex 审阅使用原生只读 sandbox；Pi 审阅限定只读工具并关闭扩展与 MCP；DSH 遵循其自身权限机制，没有额外 OS 级只读沙箱。
- 默认每周维护只处理协作台索引和临时文件，维护历史独立于工作台。真实项目、原工具会话和任务结果保留。服务关闭时错过的维护在下次启动补跑。
- 同步覆盖本地保存记录，不包含 Codex 云端或 ChatGPT 聊天。工具成功退出、轮次结束与工作已人工验收是不同状态。

请以自己的实际环境和需求为准，持续拓宽框架，同时保留清晰的任务、数据和权限边界。
